# VS Launcher physical-device benchmarks

The `macrobenchmark/` module exists only to measure VS Launcher. It is not packaged into the normal debug or release launcher APK.

## Why a separate module

Android Macrobenchmark measures another app process from a `com.android.test` module. VS Launcher therefore keeps:

- the production launcher native/platform-only
- a release-like `benchmark` app variant
- AndroidX Macrobenchmark/UIAutomator dependencies in the test module only
- ProfileInstaller in the benchmark app variant only

This lets measurements be representative without adding benchmark/runtime dependencies to the normal launcher.

## Target device

Prefer a physical Android 14+ device. Android's current Macrobenchmark guidance recommends Android 14+ for more reliable compilation-state handling.

For Nigel's current target, the Android 15+ Infinix is a suitable physical benchmark device.

Before comparing two builds:

1. use the same phone
2. use the same refresh-rate setting
3. avoid charging if it changes thermal behavior
4. start with a similar battery/thermal state
5. keep the same launcher configuration
6. close unusual background workloads
7. compare the same benchmark scenario and compilation mode

Do not treat emulator frame timings as representative device performance.

## Build prerequisites

On the computer:

- JDK 17
- Android SDK 35
- Build Tools 35.0.0
- Gradle 8.7
- ADB
- USB debugging enabled on the phone

Confirm the phone is visible:

```sh
adb devices
```

## Run the complete suite

From the repository root:

```sh
gradle --no-daemon :macrobenchmark:connectedCheck
```

The module targets the release-like `benchmark` build of `:app`.

## Included scenarios

`LauncherMacrobenchmark` measures:

1. **coldStartup**
   - cold process startup
   - `StartupTimingMetric`

2. **homeToAppsFrames**
   - Home → All Apps horizontal gesture
   - `FrameTimingMetric`

3. **homeToSettingsFrames**
   - Home → Settings horizontal gesture
   - `FrameTimingMetric`

4. **allAppsFlingFrames**
   - vertical fling in All Apps
   - `FrameTimingMetric`

5. **searchFilterFrames**
   - swipe down to focused search
   - enter a query
   - `FrameTimingMetric`

Each test currently runs eight measured iterations.

## Run one benchmark

Example:

```sh
gradle --no-daemon :macrobenchmark:connectedCheck \
  -P android.testInstrumentationRunnerArguments.class=com.vslauncher.macrobenchmark.LauncherMacrobenchmark#coldStartup
```

Replace the method name with another benchmark when isolating one path.

## Results and traces

Macrobenchmark writes JSON reports and Perfetto traces under the benchmark module's connected-test output directory. The exact device-specific subdirectory is generated by Gradle/Android Test.

Look under:

```text
macrobenchmark/build/outputs/connected_android_test_additional_output/
```

Open `*.perfetto-trace` files in Android Studio or Perfetto.

Compare at least:

- startup timing percentiles
- frame duration / frame overrun percentiles
- the same trace region before vs after a performance change

Do not claim a universal FPS based on CI or code inspection.

## CI boundary

GitHub Actions only **compiles/assembles** the benchmark module.

CI is useful for catching:

- Gradle variant errors
- Java/API compile errors
- missing dependencies
- manifest/configuration errors

CI does not run the performance suite because hosted/emulated hardware is not representative of the Infinix or another target device.

## Benchmark variant boundary

The app's special `benchmark` build type:

- derives from release behavior
- keeps minification/resource shrinking
- is non-debuggable
- is locally signed with the debug key
- is profileable only in `app/src/benchmark/AndroidManifest.xml`
- includes ProfileInstaller only for the benchmark variant

Normal debug/release launcher behavior remains separate.

## Regression workflow

For any rendering/search/startup optimization:

1. install/run benchmarks on commit A
2. save JSON + Perfetto traces
3. install/run benchmarks on commit B
4. compare the same metrics on the same phone
5. keep the change only if the regression/improvement is supported by measurement

A perceived animation difference is not enough evidence by itself.
